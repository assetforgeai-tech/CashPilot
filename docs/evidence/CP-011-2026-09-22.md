## Live canary result

Overall result: **FAIL; rollout stopped**. The canary produced useful positive
network evidence, then exposed two operational defects. No production rollout
was attempted.

- East Asia recovery: the first read-only Run Command left the VM Agent
  unresponsive. A normal restart remained stuck. Deallocate/start recovered the
  same VM and all static public IP mappings; worker and provider containers
  returned.
- Disposable runtime: Ubuntu node
  `earnapp-disposable-w118904-rotation-04` deployed through the normal API on
  worker `118904`. Provider verification remained `pending` because the account
  operation queue did not complete during this bounded run.
- Egress: repeated HTTPS egress returned the assigned proxy IP. The host packet
  capture showed the canary talking to the proxy endpoint; no direct target
  connection was observed.
- DNS/IPv6: the container resolver was `127.0.0.1`; IPv6 had a terminal DROP
  chain and the IPv6 HTTPS probe failed closed. A request to
  `https://1.1.1.1/dns-query` returned HTTP `400`, but packet capture showed
  only container traffic to the assigned proxy `51.194.83.2:1337` and no direct
  SYN/packet to `1.1.1.1`. The `400` therefore came through the proxy tunnel,
  not a direct DoH egress. DoH isolation gate is `PASS` for this canary.
- UDP: the explicit non-DNS UDP probe failed with `Operation not permitted` and
  the container `CP_EARNAPP_OUT` terminal DROP counter incremented from `0` to
  `1`; no direct UDP packet was observed. The UDP gate is `PASS` for fail-closed
  behavior.
- Watchdog/rotation: the guarded endpoint accepted exactly three unhealthy
  samples and reported `direct_fallback_blocked=true`, but returned
  `rotation_requested=false`. Gate `watchdog` is `FAIL`; the runtime was not
  silently rotated.
- Repeated worker HTTP 400 warnings were traced to the separate NKN auto-deploy
  path, not the EarnApp failure-injection route. The redacted failing route was
  `POST /api/nkn/slots/{slot_id}/deploy` on both Azure workers; the control
  plane intentionally suppressed the unstructured worker body. This noise is
  not evidence for or against EarnApp rotation and is outside CP-011 remediation.
- Reboot: Japan East returned healthy, but systemd selected
  `ghcr.io/assetforgeai-tech/cashpilot-worker:proxybase-fix-20260921` instead of
  the pre-reboot `cashpilot-phase7-worker:20260921`. This proves worker image
  persistence drift. Gate `reboot` is `FAIL`.
- Bounded follow-up reboot after installing the CP-011 pin override (authorized
  Japan East VM only) returned `cashpilot-phase7-worker:20260921`, Docker
  `running|healthy|restart=0`, and both `cashpilot-worker` and
  `cashpilot-network-slots.service` `active`. The pin persistence gate now
  passes for this isolated reboot; provider reconciliation and the remaining
  watchdog/DoH/UDP gates are still required.
- A fresh disposable Ubuntu attempt
  `earnapp-disposable-w118904-cp011-rotation-05` returned HTTP `409` with
  authenticated workload state `pending`. Immediate reconciliation showed a
  DB instance but no matching worker container. The Japan East VM remained
  `running`/`Succeeded` in Azure, but one bounded SSH retry timed out, so no
  watchdog injection or packet probe was attempted and no second canary was
  started. Watchdog remains `FAIL`; DoH is `PASS`; UDP is `PASS` for the
  observed fail-closed path.
- Earlier cleanup removed the first disposable container and rolled back its
  canary binding. A later bounded read-only verification confirmed the fresh
  `rotation-05` container absent, its logical node `PLANNED`, assigned worker,
  device, and proxy bindings null, and provider instance absent. Cleanup gate
  is `PASS`; watchdog, DoH, and UDP remain unresolved.
