# CP-oo5 — repeated stale-worker reclamation

Date: 2026-09-25. Scope: code/test only; no production mutation.

## Cause

The stale-worker scheduler revisited rows already marked `reclaimed`. Its
idempotency token includes `resource_generation`, which increases on every
reclaim. The next tick therefore generated a fresh token and another audit row.
The status update was also outside the resource-release transaction, leaving a
crash window between release and marking the worker `reclaimed`.

Read-only canonical DB observation before this change: four retired worker
rows each had roughly 1,087 historical reclamation records; no records were
deleted or altered.

## Change

- Scheduler skips terminal `reclaimed` workers.
- Resource release, generation fencing, and `status='reclaimed'` commit in one
  transaction.
- A new token for a terminal row is idempotent. Its guard checks status, not
  merely generation: a heartbeat authorized before reclaim can race its upsert
  after that transaction, leaving the row online with the same generation.
  Another legitimate stale-worker reclaim must then still release new resources.
