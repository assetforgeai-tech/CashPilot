    CP-013 staged rollout evidence - 2026-09-23¶

    Stage 3: East Asia worker canary¶

    • Scope: cashpilot-live-ea only; cashpilot-live-je unchanged.
    • Release: v1.65.0; rollback: v1.64.0 / prior worker 1.53.17.
    • Image digest verified before rollout: sha256:0f11def30bf36ce1a872e7d2e67b2c35a99b292f5b35fc071aee7606c8a0bd11.
    • Compose direct digest reference was rejected by the VM's Compose path, so the digest-verified image was loaded under the local immutable alias cashpilot-worker:cp013-v1.65.
    • First verification attempt was invalid because the operator script called /health; the worker contract is /healthz. No production failure was inferred from that bad probe.
    • The first alias rollout was rolled back without deleting volumes or provider containers.
    • Corrected retry result: old worker 2a34574d167f replaced by 3ad3b651e81d; status running; Docker health healthy; version v1.65.0; /healthz returned {"status":"ok"}.
    • Running container count remained 286 before and after; no provider container was removed.
    • Heartbeat after retry: worker logged authenticated POST /api/workers/heartbeat with HTTP 200.
    • JE was not mutated.

    Stage decision¶

    Stage 3 passed. Stop before any JE rollout or further production mutation. Next stage requires a separate JE compose/runtime audit because JE currently uses a custom dev image and historical override layers.

    Outstanding¶

    • Rotate the API key observed in diagnostic output before final acceptance.
    • Collect representative direct/proxy egress, DNS, IPv6, UDP and lease evidence before declaring production-ready.

    Stage 6: Repocket proxy-005 repair¶

    • Scope: cashpilot-live-je, one broken Repocket runtime only.
    • Root cause: the container used entrypoint=["/bin/sh", "-c", ...], but repocket/repocket is shell-less. It exited 127 continuously with exec /bin/sh failed while its egress sidecar stayed running.
    • The v1.65 renderer already contains the shell-less Repocket contract and regression test; the live container predated that fix.
    • Recreated only cashpilot-repocket-proxy-w118904-proxy-005 from its Docker metadata, retaining image, provider credentials, labels, restart policy and existing sidecar network namespace. Proxy/account inventory was not deleted or changed.
    • New container 684c11b85e1d; native entrypoint /usr/local/bin/repocket; status running; exit 0; restart count 0.
    • Runtime log confirms SDK 1.2.0, registration, stable device id 6ab347c2b708d4001181bf06, and peer connected.
    • Stage 6 passed. Stop before broader traffic/network/lease verification.

    Stage 7: acceptance sweep¶

    • Both EA and JE workers remain v1.65.0, running, Docker healthy; recent authenticated heartbeats returned HTTP 200.
    • JE Repocket-005 remains running, restart count 0, native entrypoint, and logs show peer connected.
    • JE proxy sidecars show the intended fail-closed shape: TUN auto_route, strict_route, DNS hijack, DoH over proxy-out, IPv4-only DNS strategy, no direct final route, and IPv6 only link-local TUN route.
    • A Repocket sidecar probe completed through the proxy and returned an egress address; its sing-box logs recorded DNS and outbound proxy connections. This proves traffic for that lane, not every provider lane.
    • An EarnFM proxy sidecar timed out on the same public-IP probe while DNS resolution and proxy DNS exchange succeeded. This is a provider/proxy-path acceptance failure requiring investigation; no rotation or destructive action was taken.
    • Stage 7 result: acceptance incomplete; stop before changing the EarnFM lane. API-key rotation and full provider/lease/dashboard evidence remain outstanding.

    Stage 7 follow-up: JE EarnFM proxy-010 diagnostics¶

    • Read-only inspection on cashpilot-live-je; main container and egress sidecar remained running, sidecar restart count 0.
    • Sing-box config validation passed. Routing remains fail-closed: final route proxy-out; DoH server uses proxy-out; DNS strategy ipv4_only; firewall default policy drop; only the TUN interface and exact proxy endpoint are allowed; the sole direct route rule matches only the proxy endpoint /32.
    • The configured upstream proxy TCP connection timed out from both the VM host and the sidecar network namespace. DNS lookup from the sidecar failed (getent exit 2; wget reported bad address). Therefore public HTTPS probing did not reach the target. This localizes the observed failure before provider traffic, at the upstream proxy connection/DNS dependency.
    • Azure effective route for the JE VM has 0.0.0.0/0 -> Internet; effective NSG includes AllowInternetOutBound for all protocols and ports. No Azure route/NSG egress block was found.
    • A 7-second packet capture filtered to the configured upstream proxy observed 8 outbound SYN packets and 0 SYN-ACK packets while the TCP connect timed out. A sidecar-namespace capture during failed DNS resolution observed 0 port-53 packets and 0 direct packets to the configured public DoH resolver on TCP/443. Captures retained counts only; no payload or endpoint address was recorded.
    • Final post-probe recheck after DNS, IPv6, UDP, and direct-IP tests: JE worker remained running/healthy, worker restart count 0; EarnFM proxy-010 and its sidecar remained running, restart counts 0; JE running container count remained 285 (baseline 285). EA worker remained running/healthy, restart count 0; EA running container count remained 286 (baseline 286). EA does not own the JE proxy-010 containers.
    • Current heartbeat check: /healthz returned HTTP 200 with status=ok and heartbeat present on both workers; both report Docker healthy and restart count 0.
    • Sidecar-bound network probes: the namespace had no IPv6 default route; IPv6 connect failed locally as unreachable and produced no IPv6 SYN on eth0. UDP sendto was locally accepted, but capture saw no UDP/443 or DNS packets on eth0. A TCP probe to a direct public IP timed out with no matching packet on eth0; the sidecar nft table remains default-drop and only allows TUN plus its exact upstream proxy endpoint. These are per-sidecar, per-probe fail-closed observations, not fleet-wide guarantees.
    • No direct fallback was observed or enabled by this check. The failure is fail-closed, not evidence of direct egress leakage.
    • Root cause is not yet uniquely attributable: dead proxy endpoint vs upstream network/port reachability remain indistinguishable without authoritative Proxy Pool probe/lease data. Do not rotate or rebind based only on this worker-side result.
    • Dashboard cross-check was unavailable: Computer Use returned Codex auth token is unavailable; local CDP 127.0.0.1:9222 was not listening. No dashboard mutation attempted.
    • No container, proxy, lease, provider node, credential, or VM state was changed. Stage remains blocked pending the authoritative Proxy Pool health and lease-to-instance mapping, plus key remediation approval before final acceptance.
